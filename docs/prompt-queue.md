# ChatGPT Queue 排队

AI Input History 1.31.0 起支持 ChatGPT Queue。当前一轮仍在生成时，再发送的新文本不会打断当前回复，而是进入当前会话的本地 Queue；上一轮确认结束后再按 FIFO 顺序自动发送。

## 基本行为

- ChatGPT 空闲时，Enter、发送按钮和表单提交保持原生直接发送，不经过 Queue。
- ChatGPT 正在等待或生成回复时，新文本进入 Queue。
- 悬浮按钮右键菜单可选择“禁用队列 / 启用队列”。禁用后新消息不再被 Queue 拦截，直接交给 ChatGPT 原生发送；已有排队内容不会删除，但暂停显示和自动出队，重新启用后继续处理。
- Queue 每条消息都可“编辑”“撤回”或“立即发送”。
- 自动发送只会点击 ChatGPT 明确的发送按钮，语音、麦克风和其他 submit 按钮不会作为发送目标。
- 自动发送后，只有会话 DOM 中真正新增了与 Queue 内容匹配的 user turn，才认为发送成功并移出 Queue。
- 第一条 Queue 真正发出后，后续消息继续等待这一轮回复结束，不会连续一次性全部发送。

## 异常恢复

某条 Queue 自动发送后，如果 10 秒内仍无法确认 ChatGPT 真正接收，扩展会把它标记为“发送未确认”。该消息继续保留，可重新编辑、撤回或点击“立即发送”，但它不会继续占用发送锁，后面的正常 Queue 可以继续处理。

如果 RequestTiming 因网页状态异常长期未结束，但页面已经没有生成状态且最后回复明确完成，超过 2 分钟后 Queue 不再让该旧计时阻塞新的直接发送或自动出队。也可以右键悬浮计时按钮选择“停止计时”手动清除当前观察状态。


## 1.32.1 修复

- 兼容 ChatGPT 普通会话新版 `data-chatgpt-search-unit-key` / `data-chatgpt-search-message-ids` 回复结构，Queue 能继续识别最新 assistant 回复。
- 完成判定不再把发送按钮可用单独视为强完成信号，避免回复仍生成时提前释放 Queue。
- 明确观察到生成状态结束或回复操作控件出现时立即完成；如果这些信号完全缺失，则回复正文连续稳定 10 秒后才兜底完成。

## 1.32.0 增强

- 悬浮按钮右键菜单新增“禁用队列 / 启用队列”。
- 禁用 Queue 后，新消息不再进入本地队列，即使 ChatGPT 正在回复也直接走页面原生发送。
- 已存在的 Queue 消息不会被删除；禁用期间暂停显示和自动出队，重新启用后继续处理。
- Queue 开关保存在本地设置中，刷新页面和重新打开浏览器后继续沿用。

## 1.31.3 修复

- 兼容 ChatGPT 新版 `section[data-turn="assistant"]` 回复结构，Queue 能再次正确感知上一轮回复已经结束。
- 兼容新版 `data-turn-key` / `data-conversation-role` 分组结构，以及 composer 内新的发送与停止按钮。
- 修复 ChatGPT 已经回复完成，但旧 DOM 选择器未识别到 assistant turn，导致计时持续、Queue 长时间仍判断为生成中的问题。

## 1.31.2 增强

- 当前 GPT 回复尚未结束、下一次发送会进入 Queue 时，会在 **ChatGPT 主输入框上方** 提前显示绿色状态标识“下一条将加入队列”，避免把排队误认为直接发送。
- 该提示不要求 Queue 已经有消息：即使当前是 `0` 条等待，只要下一次 Enter / 发送按钮会被 Queue 接管，就会提前显示。
- GPT 回复结束、下一次恢复直接发送后，提示会自动消失。
- 提示直接复用 Queue 的实际 `shouldQueue()` 判定，因此 UI 状态与 Enter / 发送按钮的真实行为保持一致。
- 更新扩展代码后如果提示没有出现，需要在 `chrome://extensions` 重新加载扩展，并刷新已打开的 ChatGPT 页面，让新的 content script 重新注入。

## 1.31.1 修复

- Queue 不再改变或永久中断输入框的上下历史导航状态；用户输入、移动光标或 Queue 程序化填充后，到达首尾视觉行仍可继续使用 `↑/↓` 浏览历史。
- 从历史中取出内容并再次编辑时，只重置当前历史游标；下一次方向键会以当前输入内容作为新的草稿起点继续浏览。
- “撤回” Queue 消息会把内容放回主输入框；如果输入框已有草稿，会保留两份内容并用换行分隔，避免静默覆盖。
